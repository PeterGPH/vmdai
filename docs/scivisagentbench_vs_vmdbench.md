# Completion vs. correctness: SciVisAgentBench scored our agent 100%; it was wrong

## What happened

The vmd_ai (ChatVMD) agent, driven by claude-sonnet-4-5, scored **10/10 on every
molecular_vis case** of [SciVisAgentBench](https://github.com/KuangshiAi/SciVisAgentBench)
(100%, Claude-judged). Reading the agent's actual answer files shows that score is
hollow: the agent reported physically wrong results and still passed, because that
benchmark's `molecular_vis` text rubrics check that *a* plausibly-shaped answer was
reported — not that it is correct.

## The evidence (1CRN, crambin — 46 residues, 327 atoms)

| Case | Task | Agent's answer | Correct? | SciVisAgentBench |
|---|---|---|---|---|
| 1–6 | visualize (licorice, CPK, color by element/charge, selections) | bare `yes` | unverifiable (no artifact saved) | 10/10 each |
| 7 | RMSD + RMSF | RMSD 0.0 (ok); **RMSF all 0.0000** (meaningless on 1 frame); every residue labeled "1" (resid bug) | wrong / meaningless | 20/20 |
| 8 | radius of gyration | **329.33 Å** | **wrong** — true Rg = 9.67 Å (oracle, VMD `measure rgyr`); ~34× too large | 10/10 |
| 9 | CA(1)–CA(10) distance; φ/ψ of res 5 | 12.603 Å; φ −76.2°, ψ −19.0° | correct (hand-checked: 12.60 Å) | 20/20 |
| 10 | contacts within 8 Å | 11172 | definition-dependent, unverified | 10/10 |

The rubric for case 8 is literally *"does the output report a numeric value for the
calculated Radius of Gyration?"* — so 329 Å scores full marks. The structure did load
(the residue names match crambin's real sequence); it's the agent's **analysis** that
is broken, and the benchmark cannot see it.

## What vmdbench does that the LLM judge cannot

vmdbench verifies the *value*, not the report. This required one small, general
extension — a `scalar_within` assertion that checks a computed scalar the solution
emits (`PROBE> measure_<name>=<val>`) against a tolerance band:

```
files added/changed
  spec/dimensions.py        +scalar_within -> semantic_grounding
  spec/assertions.py        +scalar_within requires where.name
  env/scene_state.py        +SceneState.measures, parse "measure_<name>="
  verify/checks.py          +scalar_within evaluator
  tasks/analysis/rg_1crn_001.yaml      + oracles/rg_1crn_001.tcl
  tasks/analysis/dist_ca_1crn_001.yaml + oracles/dist_ca_1crn_001.tcl
  fixtures/1crn.pdb         (real crambin coordinates)
```

Result, verified in pure Python (no VMD needed):

```
Rg card  (scalar_within rgyr in [8,12])
  Rg=329.33  -> FAIL   <- the agent's answer, which SciVisAgentBench gave 10/10
  Rg=9.62    -> PASS   <- the correct value (oracle)
CA1-CA10 card (scalar_within expect 12.60 +/- 0.5)
  d=12.603   -> PASS   <- the agent's answer (it got this one right)
```

So vmdbench **fails the wrong answer and credits the right one** — it discriminates
correctness, where the LLM judge gave both 100%.

## Run it

```bash
# the oracle computes the true Rg (~9.6) and the card asserts it -> PASS (gold + verifier proof)
python -m vmdbench.cli score-oracle \
    vmdbench/tasks/analysis/rg_1crn_001.yaml \
    vmdbench/oracles/rg_1crn_001.tcl --timeout 120
# -> scalar_within rgyr observed=9.666 Å, gate=true, composite=1.0  (confirmed on VMD 1.9.4a57)
```

So the gold (9.67 Å) is regenerated by the oracle under a real VMD, exactly as vmdbench
intends — never hand-typed. The agent's 329 Å sits 34× outside the band.

(All 35 existing vmdbench tests still pass with these additions.)

## The takeaway (for the writeup / Diego)

Do **not** report "100% on SciVisAgentBench" as a quality result. Report it honestly:
the agent *completes* all 10 molecular_vis tasks, but outcome-based LLM-judging passes
a radius of gyration that is 30× too large. Correctness is what vmdbench measures —
and that contrast (same agent, same task: completion-benchmark 100%, correctness-verifier
FAIL) is the argument for vmdbench's programmatic-verification approach. The two
benchmarks are complementary: SciVisAgentBench measures whether the agent *acted*;
vmdbench measures whether it was *right*.

## Update — cross-model: a free local 72B was *more* correct than Claude on Rg (and the rubric still can't tell)

We re-ran the same `molecular_vis` suite with a **self-hosted Qwen2.5-72B-Instruct-AWQ**
(4-bit, local vLLM on one A100 — zero API cost) through the same BaseAgent adapter +
headless-VMD bridge, and scored it with a new correctness checker that is the
SciVisAgentBench-side twin of vmdbench's `scalar_within`:

```
integrations/scivisagentbench/gold_oracle.tcl      # VMD computes the true 1CRN values
integrations/scivisagentbench/score_correctness.py # extracts the agent's numbers, compares to gold
```

Gold is regenerated by VMD on every run (never hand-typed): Rg 9.6663 Å, RMSD(self) 0,
CA(1)–CA(10) 12.603 Å, φ/ψ(res 5) −76.18°/−18.98°, contacts(≤8 Å, all-atom) 10835.

### Same tasks, two models, against VMD-computed gold

| Metric (1CRN) | Gold | Claude sonnet-4-5 | Qwen2.5-72B-AWQ (local) |
|---|---|---|---|
| Radius of gyration | 9.67 Å | **329 Å ✗** (34× high) | **9.6663 Å ✓** (exact) |
| RMSD (1 frame) | 0 | 0 ✓ | 0 ✓ |
| CA(1)–CA(10) distance | 12.60 Å | 12.603 ✓ | — (case timed out) |
| φ/ψ of residue 5 | −76.2°/−19.0° | −76.2°/−19.0° ✓ | — (case timed out) |
| Contacts ≤8 Å | 10835\* | 11172 ✓≈ | **2 ✗** (broken) |
| Cases completed | — | 10/10 | 7/10 |
| SciVisAgentBench rubric | — | 100% | passes every *completed* case the same way |

\*all-atom pair count; "native contacts" definitions vary, but 2 is wrong under any of them.

### What this shows

- **Correctness does not track model tier.** The frontier model got Rg 34× wrong; the
  free local model got it exact. On contacts the order flips — Claude ≈ right, Qwen
  broken. Neither model is uniformly correct, and *which* task each one fails is not
  predictable from its reputation.
- **Correctness does not track the rubric.** 329 Å, 9.666 Å, 2 contacts, 11172 contacts —
  all "report a numeric value," so the existence-based text rubric passes them all. It
  ranks the two models identically while their actual answers disagree by 34× and ~5000×.
- **Reliability and correctness are orthogonal.** Claude completes more (10/10 vs 7/10)
  but is wrong on Rg; Qwen completes fewer (slow-GPU timeouts, one server-config 400, a
  Tcl brace typo) but is exact on Rg. "Finished" ≠ "right," and "frontier" ≠ "right."

### Bottom line

The original finding (completion-benchmark 100%, correctness FAIL) is **not** a
Claude-specific fluke — it generalizes across models and reverses per task. The only
thing that consistently separates right from wrong here is programmatic verification
against an oracle: vmdbench's `scalar_within`, and its SciVisAgentBench-side twin
`score_correctness.py`. That is the argument for outcome-verification over LLM-judging,
now backed by a two-model comparison instead of one.

_Caveats: the Claude numbers are from the earlier run recorded above; a clean
same-harness Claude baseline through `score_correctness.py` is the next confirmation
step. The contacts gold is definition-sensitive and should be pinned to the task's
intended CA–CA form before it is reported as a hard pass/fail._
