VMD-AI Semantic Tools — Cross-Model Benchmark

Does a correct, brace-safe tool layer let a small local model drive VMD trajectory analysis? · ATLAS-traj benchmark · Qwen2.5 7B / 14B / 72B

Bottom line. The semantic tool vmd_traj_measure enables small models: a 7B jumps from 20% → 99% and a 14B reaches 100% correctness — matching the 72B. The values are tool-derived (exact-gold matches), so it is a scaffolding / product result (correct tools make a cheap model reliable), not a claim that the model reasons about trajectories. Surprise: tool adoption inverts with model size. But this holds only when the question names the metric. On a hard tier that hides the formulation, the same 14B collapses from 100% to 5–8% — and the tool turns actively misleading: it manufactures confident wrong answers (returns the mean when asked for the max).

The benchmark

Each task loads a protein structure + its MD trajectory and asks for one trajectory-averaged observable, scored against a gold reference computed by gold_oracle_traj.tcl. 31 chains × 5 metrics × 3 seeds = 465 checks per cell. Metrics: nframes, meanrg, meanrmsd, mean_rmsf, meansasa. Grading is programmatic (computed value within a gold-derived band) — no LLM judge. Models served locally via vLLM; two directive strengths compared: soft ("prefer tools") vs mandatory ("you must use the tool").

The 7B jumps 20% → 99%. The tool, not the model, is doing the work — the same brace-safe primitive rescues the 72B (16% → 100%) too.

Why 20%? Without a tool, only the trivial metric survives

The 7B none arm scores 100% on nframes (a one-line frame count) and essentially 0% on every real trajectory-averaged observable. The brace-heavy per-frame loop that rg/rmsd/rmsf/sasa require is exactly what a small model cannot hand-write — so the 20% overall is the nframes column. (Note the symmetry: nframes is the one "easy" metric, which is why the 72B over-trusts itself and under-adopts the tool there — see below.)

Key findings

  • The tool enables small models. 7B ≈ 99%, 14B = 100%, matching the 72B — and the values are tool-derived. A cheap local model + correct tools = reliable trajectory analysis.
  • Adoption inverts with size. The 14B adopts the tool 100% under the soft nudge — more than the 72B's 77%. The big model is confident enough to DIY the "easy" metrics and botch them; the smaller models defer. Capability can hurt tool-adoption.
  • Enforcement matters most for the big model. soft→mandatory lifts the 72B 77%→100% adoption but does nothing for the 14B (already 100%).

The hard tier: when the question hides the formulation de-saturation

The easy tier names the metric ("compute the mean radius of gyration…"), so a correct tool solves it by transcription — that is why it saturates at 100%. The hard tier instead describes a composed quantity in plain language — "how far does the backbone get from the starting structure at its most-deviated point?" (a max, not a mean) — with no metric name, formula, or VMD command. Same 14B, same fixtures; only the formulation is withheld.

The tool's rescue collapses (100% → 5–8%). Read the split carefully: on the hard tier the tool raises completion 21%→~85% (the model can always call it and get a number) but not correctness (5.4 vs none's 5.8 — within noise). It converts "can't answer" into "confidently wrong": done-but-wrong rises 76 → 388.

Why: the tool returns its one canned quantity — the mean

vmd_traj_measure mirrors the oracle, which computes means. When the hard question asks for a max or a range, the model calls the tool, gets the mean back — the wrong quantity — and reports it. The agent's answer is exactly the mean, verbatim:

caseasked forgoldagent = the mean
1h02_B rmsd_maxmax RMSD6.644.86 = meanrmsd
1h02_B rmsf_maxmax RMSF9.642.64 = mean_rmsf
2erl_A sasa_rangeSASA range2553042 = meansasa

For rmsd_max/rmsf_max/sasa_range the tool arm is 100% complete, 0% correct — every case answered, every answer the mean. A correct tool, under an underspecified question, is actively misleading: it doesn't raise correctness, it manufactures confident wrong answers. (Caveat: rg_ratio scores ~20–30% even in none because most proteins keep ratio ≈ 1.0, inside the 3% band — the one partially gameable metric. rg_std was dropped from v1 as ambiguous under the no-formula constraint; rg_argmin_frame is scored on the 11 chains with a uniquely-separated minimum.)

The bigger twist: the tool's value declines with capability gradient

Running the identical hard tier across 7B / 14B / 72B reveals two things the saturated easy tier hid. (1) With no tool, correctness ladders with model size — the benchmark now separates reasoning. (2) Adding the tool helps the weakest model a little and lowers the strongest's correctness. Hard-tier correct%:

correct% · hard tierno tool+ tool (soft)+ tool (mand)Δ from tool
7B0.82.02.0+1.2
14B5.88.05.4−0.4
72B (Int8)15.38.010.2−5.1

The none arm ladders 0.8 → 5.8 → 15.3 — de-saturation working: a capability-separating reasoning benchmark, where the easy tier had all three at ~100% with the tool. And the tool's Δ crosses zero: +1.2 (7B) → −0.4 (14B) → −5.1 (72B). A correct-but-narrow tool helps who needs it and harms who doesn't. Mechanism: unaided the 72B is calibrated — it answers the quantities it can reason (rg_delta 29%, rg_ratio 53%) and abstains on the rest (10 errors in 498); the tool overwrites that (reports the mean, fills abstentions with confident-wrong: errors 10 → 291). The 7B is too weak to reason or wield the tool — near-floor either way. Universal: with the tool all three hit high completion but low correctness — the "confidently wrong" wall spans the whole capability range. It closes the loop with the easy tier: the 72B's tool under-adoption (77% vs 14B's 100%) was a flaw there, a virtue here. (Caveat: on pure max/range metrics even the 72B abstains rather than hand-write a Tcl max-loop — a Tcl-fluency barrier; a Python-substrate re-run would separate it from reasoning.)

The fix: a composable workbench + faithful recording give data, not answers

The canned tool fails because it returns a fixed answer (the mean). The workbench returns data — vmd_traj_series gives the raw per-frame series, and vmd_compute safe-evaluates a reduction the model writes itself (max(rmsd), rgyr[-1]-rgyr[0], ptp(sasa)). v2 adds save_path: the tool writes its computed value straight to the answer file, so a correct reduction becomes a correctly recorded answer. Hard-tier correct% (SEEDS=3; 7B CONC=8, 14B/72B CONC=2; models provenance-verified):

hard tier · correct%7B14B72B (Int8)

canned tool2.45.29.8
workbench v130.939.644.6
workbench v2 (+save_path)36.781.3100.0
v2 completion%39100100

v2 exposes two capability barriers. Fixing the write path lifts the 14B (39.6→81.3) and 72B (44.6→100) enormously, but the 7B only inches up (30.9→36.7) — its bottleneck is earlier: it completes only 39% (a tool-orchestration barrier — it can't reliably sequence fetch→compute→record), while the 14B/72B complete 100%. With recording removed as a factor, the residual gap is pure reduction reasoning: the 14B's ~19% remaining errors are genuine wrong-quantity picks (e.g. reaching for RMSD on a size question), which the 72B doesn't make. So capability grades cleanly — orchestration (7B fails), then reduction choice (14B occasionally fails), then perfect (72B). (An earlier "precision falls with size" read was a v1 write-fumble artifact — v2 corrects it: the 72B's reasoning was already near-perfect.) The flip side: workbench v2 re-saturates the hard tier for the 72B — an oracle-capable tool re-saturates once the model can drive it, motivating a harder tier.

Honest caveats

Read these before quoting the numbers.

  • Tool = oracle. vmd_traj_measure's Tcl mirrors the gold reference, so it measures tool design + adoption, not the model's analysis reasoning. The benchmark hands over the formulation (it names the metric); it only tests execution.
  • Quantization confound. The 72B here is AWQ (4-bit); the 7B/14B are full precision. The "capability under-adopts" claim needs a full-precision 72B to rule out quantization.
  • Code-path confound. The 72B soft/mandatory cells were produced by older harness code than the 7B/14B; a clean re-run through the identical path is pending.
  • Adoption% is inferred, not measured. Read from transcripts, it under-counts tool-use for small models (they interleave inspection/failed run_vmd_command calls). The tool-derived% column is the reliable signal; direct per-case tool-call logging is the fix.
